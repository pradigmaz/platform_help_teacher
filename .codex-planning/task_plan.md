# План: индикаторы заполненности посещаемости в расписании

Статус: закрыт.

## Цель

Сделать так, чтобы в карточках админского расписания было видно:

- где посещаемость полностью выставлена;
- где выставлена частично;
- где посещаемость не выставлялась вообще;
- при этом не подсвечивать будущие занятия, включая те, что ещё не прошли на текущей неделе.

## Зачем

Основной сценарий: быстро пролистывать текущую и прошлые недели и сразу видеть, где преподаватель не закрыл посещаемость, а где всё в порядке.

## Критерии готовности

- В расписании у каждой прошедшей карточки есть понятный статус заполненности посещаемости.
- Будущие занятия не помечаются как пропущенные по заполнению.
- Для текущего дня карточка начинает считаться "прошедшей" только после окончания соответствующей пары.
- Для подгрупп expected-count считается по релевантным студентам, а не по всей группе.
- Для grouped lecture статус считается по всем lesson rows внутри карточки.
- Есть тесты или проверяемые сценарии на `none / partial / complete / hidden-for-future`.

## Зафиксированные правила

- Подсвечивать только занятия, которые уже прошли.
- Для определения "прошло / не прошло" использовать МСК и время окончания пары.
- Для прошлых недель подсветка нужна всегда, если занятие не отменено.
- Для будущих дней текущей недели и будущих недель индикатор незаполненности не показывать.
- Отменённые занятия не должны попадать в список "профакапился".
- `Не отмечено` в журнале отличается от `ABSENT`: отсутствие записи = посещаемость не выставлялась.

## Рекомендуемая модель состояния карточки

- `hidden`
  - занятие ещё не прошло, индикатор не показываем;
- `not_applicable`
  - отменено;
- `unmarked`
  - ожидаются записи, но их нет;
- `partial`
  - записи есть, но не на всех ожидаемых студентах;
- `complete`
  - записи есть на всех ожидаемых студентах.

Примечание:
`ended_early` не отменяет необходимость заполнить посещаемость; такое занятие остаётся обычным кандидатом на `unmarked/partial/complete`.

## Архитектурное решение

Рекомендуемый путь: считать summary на backend и отдавать его в `/admin/schedule/view`.

Почему:

- не будет N+1 запросов на каждую карточку;
- логика expected-count и past/future будет централизована;
- grouped lectures можно агрегировать один раз на сервере;
- фронт сведётся к отображению уже готового состояния.

## Риски

- В текущем `ScheduleViewResponse` нет summary вообще; без backend-расширения фронт будет вынужден делать дорогие дополнительные запросы.
- `admin/groups/{group_id}/students` сейчас не возвращает `subgroup`; для lesson summary это может быть недостаточно, если использовать именно этот endpoint.
- grouped lecture собирается как набор обычных `Lesson` по `(date, lesson_number, subject_id)`, поэтому summary нужно агрегировать поверх нескольких `lesson_id`, а не пытаться считать по одной сущности.
- Текущее визуальное определение `past` в `ScheduleGrid` основано на `isPast(date)` и не учитывает время окончания пары в текущий день; для твоего сценария этого недостаточно.

## Порядок реализации

1. Backend summary calculator + past logic.
2. Расширение `/admin/schedule/view` и схем.
3. Подключение новых полей во фронт.
4. Визуализация в карточках и легенде.
5. Тесты и ручная проверка на нескольких неделях.

## Минимальный MVP

- Summary только для `lessons`.
- Для `grouped_lectures` временно показывать summary после агрегирования по внутренним group lessons без дополнительных деталей.
- Подсветка только иконкой/маленьким бейджем без отдельной новой панели.

## Что не делать

- Не считать будущие занятия "не заполненными".
- Не приравнивать отсутствие записи к `ABSENT`.
- Не тащить по одному attendance-запросу на каждую карточку недели.
- Не завязывать past/future только на дату без времени пары.
