3. Backend runtime environment

Боевой backend venv не используется как общий полигон для всего тестового стека.

Причина:

- backend закреплён на pytest==8.3.4;
- Schemathesis 4.14.1 требует pytest>=9;
- прямое смешивание этих зависимостей в backend/venv создаёт конфликт с текущим стеком.

После восстановления и проверки:

- `cd backend && ./venv/bin/pip check`
- результат: `No broken requirements found.`

Важное архитектурное решение

Тестовые инструменты разделены на два слоя:

- runtime/dev env проекта;
- tool env для тяжёлых тестовых инструментов и исследовательских прогонов.

Это сделано намеренно. Самая опасная ошибка здесь — засунуть весь тестовый стек прямо в backend/venv и сломать совместимость runtime-зависимостей.

Матрица тестов: что чем бить

1. Контрактные и API-тесты

Инструменты:

- pytest
- FastAPI TestClient
- Schemathesis

Что ловят:

- позитивные и негативные сценарии;
- несовпадение OpenAPI и реального поведения;
- ошибки сериализации;
- недостающие валидации;
- edge cases по query/body/path parameters.

2. Property-based тесты

Инструменты:

- Hypothesis
- fast-check для frontend-логики

Что ловят:

- скрытые граничные дефекты;
- нестабильные инварианты;
- кривые state transitions;
- ошибки нормализации, санитайза и бизнес-расчётов.

3. Интеграционные тесты

Инструменты:

- pytest
- testcontainers
- реальные Postgres / Redis / при необходимости другие контейнеры

Что ловят:

- расхождение между unit-предположениями и реальной инфраструктурой;
- ошибки конфигурации;
- migration/runtime проблемы;
- реальные транзакционные и session-boundary дефекты.

4. Системные и E2E тесты

Инструменты:

- Playwright

Что ловят:

- реальные пользовательские поломки по критическим сценариям;
- регрессии в auth/session/impersonation;
- ошибки маршрутизации, hydration и формы;
- расхождение frontend-backend контракта.

5. Нагрузочные и деградационные тесты

Инструменты:

- k6

Что ловят:

- slow queries;
- saturation под серией запросов;
- деградацию latency на audit/admin/journal ручках;
- проблемы с concurrency и pool sizing.

6. Security negative testing

Опора:

- OWASP WSTG

Что ловят:

- auth/session/csrf flaws;
- permission bypass;
- input abuse;
- небезопасные error paths;
- технический шум, который зря тащится в БД и логи.

7. Проверка качества самих тестов

Инструменты:

- mutmut

Что ловит:

- тесты, которые зелёные, но не чувствительны к реальным мутациям логики;
- ложное ощущение «всё покрыто».

Приоритетная программа именно для этого репозитория

Волна 1:

- backend negative и boundary tests на auth, audit, attendance, labs;
- Hypothesis на нормализацию fingerprint, sanitizer, deadline/attestation logic;
- Playwright smoke на login, student critical paths, admin journal/audit;
- интеграционные тесты через testcontainers для Postgres и Redis.

Волна 2:

- Schemathesis against OpenAPI для automated negative/edge coverage;
- k6 на горячие чтения и записи;
- security negative set по OWASP WSTG.

Волна 3:

- mutmut на самые рискованные backend-модули;
- расширение property-based тестов на все инвариантные бизнес-модули.

Что не делать

- не ставить Schemathesis и другие тяжёлые инструменты прямо в backend/venv, если это ломает pinned стек проекта;
- не смешивать runtime-deps и experimental test-deps в одном окружении;
- не писать тесты ради покрытия, которые ничего не ломают при реальной ошибке;
- не считать зелёный unit-suite достаточным без негативных, интеграционных и системных проверок.
